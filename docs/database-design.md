# Snackify database design

PostgreSQL is the single source of truth for the web and Android apps. Clients never connect to
it directly; every operation goes through the backend API.

## Conventions

| Topic             | Rule                                                                              |
| ----------------- | --------------------------------------------------------------------------------- |
| Primary keys      | `uuid` generated by the database (`gen_random_uuid()`)                            |
| Money             | `numeric(12, 2)`, never floating point. The API returns it as a decimal string    |
| Timestamps        | `timestamptz`, stored and compared in UTC (both roles use `timezone = 'UTC'`)     |
| Business dates    | `date` columns; "today" is worked out explicitly in `Africa/Harare`, not by the server's clock setting. The API returns dates as `YYYY-MM-DD` strings |
| `updated_at`      | Kept current by the `set_updated_at()` trigger, not by application code          |
| Rules             | Enforced with `CHECK`, `UNIQUE` and foreign-key constraints, named `<table>_<rule>` so errors are easy to map to messages |
| Deleting          | Records referenced by history are deactivated (`is_active = false`), never deleted |
| Schema changes    | Only through migrations in `database/migrations/`; never by editing a database by hand |

## Roles and least privilege

| Role             | Used by                  | Can do                                                    |
| ---------------- | ------------------------ | --------------------------------------------------------- |
| `postgres`       | Administrator only       | Everything (local install's superuser)                    |
| `snackify_owner` | Migrations               | Owns the databases and tables; creates and changes tables |
| `snackify_app`   | The API at runtime       | `SELECT`, `INSERT`, `UPDATE` (and `DELETE` only where a migration allows it). Cannot create, alter or drop tables, or read the migration history |

New tables created by migrations are automatically readable and writable by `snackify_app`
(default privileges set in `database/setup/setup-database.sql`). A migration removes privileges
where a rule demands it, for example `products` has no `DELETE`.

Databases: `snackify_dev` (development), `snackify_test` (automated tests; wiped by them) and
`snackify_restore_check` (empty; backups are test-restored into it and it is wiped again, see
[backup-and-restore.md](backup-and-restore.md)).

## Tables

### `products` — one row per sellable variation (spec 6.2)

Example: "Potato Crisps — BBQ — Small" and "Potato Crisps — BBQ — Large" are two rows.

| Column          | Type            | Rules                                                        |
| --------------- | --------------- | ------------------------------------------------------------ |
| `id`            | `uuid`          | Primary key                                                  |
| `sku`           | `text`          | Required, unique, upper case: `A-Z 0-9 . _ -`, up to 40 chars |
| `name`          | `text`          | Required, trimmed, 1–100 chars                               |
| `flavour`       | `text`          | Required, trimmed, 1–60 chars                                |
| `size`          | `text`          | Required, trimmed, 1–40 chars                                |
| `barcode`       | `text`          | Optional; unique when present; letters, digits, `-`, 4–48 chars |
| `default_price` | `numeric(12,2)` | Required, `>= 0`, in the business's base currency            |
| `reorder_level` | `integer`       | Optional, `>= 0`. Stock at or below it is "low"              |
| `safety_stock`  | `integer`       | `>= 0`, default 0. Kept on top of forecast demand (spec 6.11) |
| `is_active`     | `boolean`       | Defaults to `true`                                           |
| `created_at`    | `timestamptz`   | Set on insert                                                |
| `updated_at`    | `timestamptz`   | Updated automatically on every change                        |

Also: the same name + flavour + size cannot be registered twice (ignoring letter case), and the
API role cannot delete products; they are deactivated instead.

**Barcodes (spec 6.7):** a barcode is either the manufacturer's or one of Snackify's own,
generated for packs without one: EAN-13 codes `20` + a 10-digit number from
`internal_barcode_seq` + a check digit (prefix 20 is reserved by GS1 for use inside a business,
so it never clashes with a manufacturer's code). The unique constraint on `barcode` covers both
kinds; when the next number is already used by another product, it is skipped.

Transactions (dispatch lines, invoice lines) will store their own price and currency snapshot, so
changing `default_price` never rewrites history.

### `users`: staff accounts (spec 5 and 6.1)

| Column          | Type          | Rules                                                          |
| --------------- | ------------- | -------------------------------------------------------------- |
| `id`            | `uuid`        | Primary key                                                    |
| `username`      | `text`        | Required, unique, lower case: `a-z 0-9 . _ -`, 3–32 chars      |
| `full_name`     | `text`        | Required, trimmed, 1–100 chars                                 |
| `organisation_id` | `uuid`      | Required; references `organisations`. Where the person works   |
| `role`          | `text`        | Old single role, kept for history only (null for new accounts); roles are in `user_roles` |
| `password_hash` | `text`        | Must be an Argon2id hash (`$argon2id$...`); plain text is rejected |
| `is_active`     | `boolean`     | Defaults to `true`. Inactive accounts cannot sign in           |
| `created_at`    | `timestamptz` | Set on insert                                                  |
| `updated_at`    | `timestamptz` | Updated automatically on every change                          |

The API role cannot delete accounts; they are deactivated instead, so the audit log always
points at a real person. Staff of a deactivated organisation cannot sign in either.

### `organisations`: the Head Office and its subsidiaries (StockFlow Stage 3)

| Column              | Type          | Rules                                                      |
| ------------------- | ------------- | ---------------------------------------------------------- |
| `id`                | `uuid`        | Primary key                                                |
| `code`              | `text`        | Required, unique, upper case: `A-Z 0-9 _ -`, 2–20 chars    |
| `name`              | `text`        | Required, trimmed, 1–120 chars                             |
| `organisation_type` | `text`        | `HQ` or `SUBSIDIARY`; exactly one `HQ` (partial unique index) |
| `is_active`         | `boolean`     | The Head Office is always active                           |
| `contact_name`, `contact_phone`, `contact_email`, `address` | `text` | Optional, checked formats |
| `billing_name`, `billing_address`, `tax_number` | `text` | Optional                           |
| `created_at`, `updated_at` | `timestamptz` |                                                 |

Never deleted (the API role has no `DELETE`). The function `hq_organisation_id()` returns the
Head Office's id; it is the default owner of stock recorded by the existing screens.

### `permissions`, `roles`, `role_permissions`, `user_roles`

- `permissions`: one row per permission code the API checks (e.g. `stock.receive`). The list is
  defined by the code (`backend/src/modules/auth/permissions.ts`; a test checks they match), so
  the API role cannot change it.
- `roles`: `code`, `name`, `description`, `organisation_type` (which kind of organisation's staff
  may hold it).
- `role_permissions`: which permissions each role has. Data, not code: changed through
  `PUT /api/v1/roles/:code/permissions`.
- `user_roles`: which roles each user holds (`granted_by`, `granted_at`). A trigger refuses a role
  that does not suit the user's organisation type (`user_roles_organisation_type`), also when a
  user is moved to another organisation.

### `sessions`: signed-in devices

| Column       | Type          | Rules                                                    |
| ------------ | ------------- | -------------------------------------------------------- |
| `id`         | `uuid`        | Primary key                                              |
| `user_id`    | `uuid`        | References `users`                                       |
| `token_hash` | `bytea`       | SHA-256 of the session token (32 bytes), unique          |
| `created_at` | `timestamptz` | When the user signed in                                  |
| `expires_at` | `timestamptz` | 12 hours after sign-in; must be after `created_at`       |
| `revoked_at` | `timestamptz` | Set on sign-out, password change/reset or deactivation   |

The token itself is never stored, so a copy of the database cannot be used to sign in.

### `audit_logs`: who did what, and when (append-only)

| Column          | Type          | Rules                                                          |
| --------------- | ------------- | -------------------------------------------------------------- |
| `id`            | `uuid`        | Primary key                                                    |
| `occurred_at`   | `timestamptz` | When it happened                                               |
| `actor_user_id` | `uuid`        | Who did it; `NULL` for the setup command or unknown usernames  |
| `action`        | `text`        | e.g. `auth.login`, `auth.login_failed`, `user.created`         |
| `entity_type`   | `text`        | What was affected, e.g. `user`                                 |
| `entity_id`     | `uuid`        | Which record was affected                                      |
| `details`       | `jsonb`       | Extra facts, e.g. `{"from": ["hq_sales_officer"], "to": ["system_admin"]}` |
| `organisation_id` | `uuid`      | The organisation the action was for or by (StockFlow Stage 3)  |
| `ip_address`    | `inet`        | The client's network address                                   |

The API role can add entries but cannot change or delete them. Passwords and tokens are never
written to the log.

### `stock_batches`: stock received (spec 6.3)

One row per delivery of one product, or per opening balance. Never edited: mistakes are corrected
with an adjustment in the ledger, so the original record stays.

| Column               | Type          | Rules                                                  |
| -------------------- | ------------- | ------------------------------------------------------ |
| `id`                 | `uuid`        | Primary key                                            |
| `product_id`         | `uuid`        | References `products`                                  |
| `quantity_received`  | `integer`     | `> 0` (packs)                                          |
| `received_date`      | `date`        | Business day it arrived; the API refuses future dates  |
| `batch_number`       | `text`        | Optional, 1–60 chars                                   |
| `expiry_date`        | `date`        | Optional; not before `received_date`                   |
| `supplier_reference` | `text`        | Optional supplier or delivery-note number, 1–120 chars |
| `is_opening_balance` | `boolean`     | Stock already on the shelf before Snackify was used    |
| `received_by`        | `uuid`        | References `users`                                     |
| `created_at`         | `timestamptz` | When it was recorded                                   |

### `stock_movements`: the stock ledger (spec 6.4), append-only

| Column                 | Type          | Rules                                                     |
| ---------------------- | ------------- | --------------------------------------------------------- |
| `id`                   | `uuid`        | Primary key                                               |
| `product_id`           | `uuid`        | References `products`                                     |
| `batch_id`             | `uuid`        | The receipt, for `receipt` and `opening_balance` (required) |
| `movement_type`        | `text`        | `opening_balance`, `receipt`, `dispatch`, `customer_return`, `damage`, `adjustment`, `reversal` |
| `quantity_delta`       | `integer`     | Never 0. Must be positive for receipts, opening balances and returns, negative for dispatches and damage |
| `business_date`        | `date`        | The business day it belongs to                            |
| `occurred_at`          | `timestamptz` | When it was recorded                                      |
| `created_by`           | `uuid`        | References `users`                                        |
| `reference`            | `text`        | A document number, e.g. a delivery note                   |
| `reason`               | `text`        | Required (3–500 chars) for damage, adjustments, reversals |
| `reverses_movement_id` | `uuid`        | For reversals (later stages); each movement reversed at most once |

Indexed by product and date. The API role can add rows but never change or delete them.

**Ownership (StockFlow Stage 3).** Every batch and movement has an `owner_organisation_id`
(default: the Head Office). A movement of a batch always has the batch's owner (composite
foreign key). Where stock is kept is not who owns it.

**Stock on hand (StockFlow Stage 4).** The `stock_balances` **table** holds one row per product,
owner, warehouse and batch (`UNIQUE NULLS NOT DISTINCT`; unbatched stock has a null batch), with
`quantity_on_hand >= 0` and `0 <= quantity_reserved <= quantity_on_hand`. A `SECURITY DEFINER`
trigger on `stock_movements` updates it in the same statement as each movement, so it always
equals the sum of the ledger (a database test checks this); the API role can read it but never
write it. The view `hq_stock_on_hand` (product, on hand, reserved) is the **Head Office's**
stock, which dispatches, forecasts and reports use, so the Head Office can never dispatch a
subsidiary's goods. Stock leaves the earliest-expiring batch first (FEFO). The migration filled
the table from the existing ledger, giving the remaining stock to the newest batches.

Movements gained (Stage 4): `warehouse_id` (default: the default warehouse), `unit_id` and
`entered_quantity` (what was typed when not the base unit), `related_document_type`/`_id` (e.g.
the goods-received note), and `movement_number` (`M0000001`, unique, from a sequence). New
types `custody_release`, `internal_transfer` and `return_to_supplier` are reserved for later.

**Never below zero, even under concurrency:** every operation that changes stock first locks the
product's row (`SELECT … FOR UPDATE`), checks the balance, and then writes the movement in the
same transaction. Two people removing the same product's stock at the same moment are therefore
handled one after the other. `npm run test:db` checks this by sending 20 simultaneous removals.

### Catalogue (StockFlow Stage 4)

- `product_categories`: `name` (unique ignoring case), `is_active`. Products gain
  `description`, `category_id` and `base_unit_id` (default: pack; fixed once the product has
  movements).
- `units`: `code` (unique, lower case), `name`; seeded `pack`, `carton`, `case`.
- `unit_conversions`: per product, `unit_id` → `base_quantity` (2–100,000 base units), never
  the product's own base unit (trigger). Quantities are converted exactly, in whole base units.
- `suppliers`: `code` (unique, `^[A-Z0-9][A-Z0-9_-]{1,19}$`), name, contact name, phone, email,
  address, `is_active`.
- `warehouses`: `code`, name, address, `organisation_id`, `is_default` (exactly one, always
  active); seeded `HQ-MAIN`. Batches and movements record their warehouse.

Nothing in these tables is deleted by the app; entries are deactivated.

### `stock_receipts`, `stock_receipt_lines`, `stock_receipt_attachments` (StockFlow Stage 4)

A goods-received note per delivery: `grn_number` (`GRN000001`, from a sequence), the owner
organisation, warehouse, supplier, supplier invoice number, purchase and received dates,
currency, notes, `status` (`DRAFT`, `PENDING_VERIFICATION`, `VERIFIED`, `REJECTED`, `POSTED`,
`REVERSED`), who received, submitted, posted, verified, rejected and reversed it (with when and
why), and `no_document_reason`. CHECK constraints require what each status needs (e.g. a
submitted receipt has a supplier; a rejected one a reason).

- Trigger `stock_receipts_protect`: only the allowed status steps, and none of the header
  fields change after the draft.
- Lines: product, unit, `quantity_purchased`, `quantity_received`, `base_quantity_received`,
  `unit_cost numeric(14,4)`, `line_total numeric(14,2)` (CHECK: `= round(quantity_purchased *
  unit_cost, 2)`), batch number, expiry, `discrepancy_reason` (required exactly when the two
  quantities differ), and the delivery batch created when posted (`batch_id`). Trigger: lines
  change only while the receipt is a draft (apart from recording the batch).
- `stock_batches.receipt_line_id` (unique) links each delivery batch to its line.
- Attachments: original file name, `storage_key` (64 random hex characters: the file's name on
  disk), `mime_type` (PDF, JPEG, PNG: checked from the content), size, `sha256`, uploader,
  `verification_status` (`PENDING`, `VERIFIED`, `REJECTED` with a reason), reviewer, review
  notes, and the `document_total` the reviewer read. The API role cannot delete them.

### `orders`, `order_items`, `order_status_history`, `order_item_changes` (StockFlow Stage 5)

- `orders`: `order_number` (`ORD000001`, from a sequence), `organisation_id` (a subsidiary only:
  trigger), order and required dates, requested by, currency, notes, `status`,
  `idempotency_key` (unique per person: a repeated request finds the first order),
  `tax_amount`/`discount_amount` (hooks, 0), who submitted, decided (with comment and
  `price_exception_approved`) and cancelled (with reason). CHECKs: a rejection has a comment, a
  cancellation a reason, a decided order a decision time. Never deleted.
- `order_items`: product, unit, `requested_quantity` and `base_quantity` (in packs),
  `expected_unit_price`, `maximum_unit_price` (≥ expected), `actual_unit_price` (set by the
  Head Office); **generated** columns `expected_line_total`, `maximum_line_total`,
  `actual_line_total` and `price_exception` (actual > maximum), so the database itself works
  them out. A product and unit appear once per order.
- Trigger `orders_protect`: only the allowed status steps; a submitted order's details never
  change. Trigger `order_items_protect`: lines change only in a draft; afterwards only the
  actual price, and only while submitted or under review.
- `order_status_history` (from, to, who, when, comment) and `order_item_changes` (line, field,
  old, new, who, when, comment): the API role may only add rows, never change or delete them.

### `customers` (spec 6.5)

Only what billing and deliveries need; no other personal details. Never deleted (the API role has
no `DELETE`), so dispatch and invoice history always points at a real customer.

| Column         | Type            | Rules                                                     |
| -------------- | --------------- | --------------------------------------------------------- |
| `id`           | `uuid`          | Primary key                                               |
| `code`         | `text`          | Unique, upper case, up to 20 chars. Generated as `C0001`, `C0002`, … from `customer_code_seq` when not given (skipping codes already used) |
| `name`         | `text`          | Required, trimmed, 1–120 chars                            |
| `phone`        | `text`          | Optional; digits, spaces, brackets, dashes, optional `+`  |
| `address`      | `text`          | Optional delivery address, 1–300 chars                    |
| `credit_limit` | `numeric(12,2)` | Optional, `>= 0`, base currency; `NULL` = no limit set    |
| `is_active`    | `boolean`       | Defaults to `true`                                        |
| `created_at`   | `timestamptz`   | Set on insert                                             |
| `updated_at`   | `timestamptz`   | Updated automatically on every change                     |
| `organisation_id` | `uuid`       | The subsidiary this customer record stands for (unique); `NULL` for customers added before Stage 3 |

Which permissions may change which columns is enforced by the API (see the API documentation).
Since StockFlow Stage 3 the buyers are the subsidiaries (decision D1): customer records are
created with each subsidiary, not on their own.

### `dispatches` and `dispatch_items` (spec 6.6)

`dispatches` is the header: `dispatch_number` (unique, `D000001`… from `dispatch_number_seq`,
given when the draft is created), `customer_id`, `status` (`draft`, `confirmed`, `cancelled`,
`reversed`), `dispatch_date` (business day the goods leave), optional `notes`, and who/when for
each step: `created_by/at`, `confirmed_by/at`, `cancelled_by/at` + `cancel_reason`,
`reversed_by/at` + `reversal_reason`. Check constraints require the who/when (and a reason) that
belong to each status. `confirmed_over_credit_limit` records a credit-limit override.

`dispatch_items` holds one line per product (`UNIQUE (dispatch_id, product_id)`): `quantity`
(`> 0`) and `unit_price` (`numeric(12,2)`, `>= 0`), the price agreed for this dispatch. It is a
snapshot: later changes to the product's default price never alter it.

Indexed by customer and date, and by status and date.

**Never edited after confirmation, enforced by the database:**

- A trigger on `dispatches` refuses any change to a confirmed, cancelled or reversed dispatch,
  except confirmed → reversed (with nothing else changed).
- A trigger on `dispatch_items` refuses inserting, changing or deleting lines unless the
  dispatch is still a draft.
- The API role has no `DELETE` on `dispatches`.

**Stock:** confirming writes one `dispatch` movement per line into `stock_movements`
(`quantity_delta` negative, `reference` = dispatch number, `dispatch_item_id` = the line).
Reversing writes matching `reversal` movements (`reverses_movement_id` → the original, unique so
nothing is reversed twice). Confirming locks the dispatch, the customer and every product on it
(always in the same order, so two confirmations cannot deadlock) before checking stock.

### `invoices` and `invoice_items` (spec 6.8)

`invoices` is the header: `customer_id`, `status` (`draft`, `issued`, `voided`), the billing
period (`period_from`, `period_to`, both included), `currency` (three letters, from
`BASE_CURRENCY`), `subtotal` and `total` (`numeric(14,2)`; `total = subtotal` until discounts
exist), and who/when for each step: `created_by/at`, `issued_by/at`, `voided_by/at` +
`void_reason`. `invoice_number` (unique, `INV-000001`… from `invoice_number_seq`),
`issue_date` and `due_date` (issue date + `PAYMENT_TERMS_DAYS`, default 7) are set when the
invoice is issued, so voided drafts never leave gaps in the numbering. Issuing also copies the customer's code, name, phone and address into `customer_*`
columns: the details printed on the invoice, which later customer changes never alter. Check
constraints require the number, date, snapshot and who/when for issued invoices, and the
who/when and a reason for voided ones.

`invoice_items` holds one row per billed dispatch line, as a snapshot: `dispatch_item_id`,
`dispatch_number`, `dispatch_date`, `product_id`, `sku`, `description` (product — flavour —
size), `quantity`, `unit_price` and `line_total` (checked to equal quantity × unit price).

Indexed by customer and period, by status and issue date, by customer and due date (issued
invoices, for overdue balances), and by invoice (for the lines).

**Never billed twice:** `UNIQUE (dispatch_item_id)` on `invoice_items` means a dispatch line can
be on only one invoice. Creating a draft also locks the customer (`FOR UPDATE`) and the
dispatches being billed (`FOR SHARE`, so they cannot be reversed at the same moment). Voiding a
draft deletes its lines, which releases those dispatch lines to be invoiced again.

**Issued invoices never change, enforced by the database:**

- A trigger on `invoices` refuses any change to an issued or voided invoice. When a draft is
  issued, it also checks that the subtotal equals the sum of the lines and is above zero
  (spec 11: invoice totals equal the sum of the lines).
- A trigger on `invoice_items` refuses inserting, changing or deleting lines unless the invoice
  is still a draft.
- The API role has no `DELETE` on `invoices`.

**Billing week:** the API's default period is the last complete week in the business time zone
(`BUSINESS_TIMEZONE`, default `Africa/Harare`), with weeks starting on `BILLING_WEEK_STARTS_ON`
(default Monday). Dates are calendar dates (`date`), so no time-zone conversion applies to them.

### `payments` and `payment_allocations` (spec 6.9)

`payments` records money received: `payment_number` (unique receipt number `P000001`… from
`payment_number_seq`), `customer_id`, `payment_date` (the business day it was received),
`amount` (`numeric(14,2)`, above zero), `currency` (from `BASE_CURRENCY`), `method` (`cash`,
`bank_transfer`, `mobile_money`, `card`, `cheque`, `other`), optional `reference` and `notes`,
`recorded_by` and `created_at`. `status` is `recorded` or `voided` (with `voided_by/at` and a
`void_reason`, required by a check constraint). `idempotency_key` (unique, optional) is chosen by
the app for each new payment, so a request that arrives twice records one payment.

`payment_allocations` says how much of a payment pays which invoice: `payment_id`,
`invoice_id`, `amount` (above zero), `created_by/at`. A payment can pay several invoices and an
invoice can be paid by several payments. Whatever is not allocated is credit on the customer's
account.

Indexed by customer and date, by date, and allocations by payment and by invoice.

**Enforced by the database:**

- A trigger on `payments` allows only one change: `recorded` → `voided`, with nothing else
  altered. The API role has no `DELETE` on payments, and no `UPDATE` or `DELETE` on allocations.
- A trigger on `payment_allocations` locks the payment and then the invoice (the order the API
  uses), and refuses an allocation when the payment is voided, the invoice is not the same
  customer's issued invoice in the same currency, the payment's allocations would exceed its
  amount, or the invoice would be paid beyond its total. Locking first means allocations made at
  the same moment are checked one after the other.
- Voiding a payment keeps its allocations as history; they stop counting because only
  allocations of `recorded` payments are added up.

**Views:** `invoice_amounts_paid` (per invoice, the sum of allocations from recorded payments)
and `payment_amounts_allocated` (per payment, the sum of its allocations). An invoice's balance
due is `total - amount_paid`.

**What a customer owes** is computed, not stored: confirmed dispatches not yet on an issued
invoice, plus what is unpaid on issued invoices, less unallocated credit. This equals the value
of confirmed dispatches less payments received, which is also the balance used for credit-limit
warnings.

### `forecast_runs` and `forecasts` (spec 6.11)

`forecast_runs` records each time a forecast was made: `forecast_start` (the first day forecast,
the business day it was made), `method` (`weekday-average`), `created_by` and `created_at`.

`forecasts` holds one row per product and horizon in a run: `product_id`, `forecast_start`,
`horizon_days` (7 or 30), `method`, `status` (`ok`, `insufficient_history`, `no_history`),
`predicted_quantity` (`numeric(12,1)`), `lower_quantity` and `upper_quantity` (a rough 80%
range), and the history it had (`history_days`, `weeks_used`). Check constraints require a
prediction and range exactly when the status is `ok`, with lower <= predicted <= upper.
`UNIQUE (run_id, product_id, horizon_days)`; indexed by product, horizon and start date for
comparing past forecasts with what was dispatched.

Both are append-only: the API role has no `UPDATE` or `DELETE` on them, so a forecast is
always kept as it was made. Demand itself is not stored: it is read from confirmed dispatches.

## Migrations

Migrations are plain SQL files in `database/migrations/`, run by
[node-pg-migrate](https://github.com/salsita/node-pg-migrate). Each file has an
`-- Up Migration` section and a `-- Down Migration` section. Applied migrations are recorded in
the `schema_migrations` table. All pending migrations run in one transaction, so a failure
changes nothing.

Rules:

- Never edit a migration that has been applied anywhere outside your own machine. Add a new one.
- Every migration must also run cleanly backwards (`npm run test:db` rolls back and re-applies
  them all).
- Rollback is disabled in production; fix mistakes with a new forward migration.
